# ADR-0010: 업무일지의 대상 판정을 계정 ID와 권한으로 함

- 상태: **Accepted**
- 날짜: 2026-10-10
- 관계: [ADR-0004](0004-evolve-authorization-only-from-consuming-domain-requirements.md)의 "소비 도메인의 요구가 생길 때 확장"을 적용한 첫 사례

## 맥락

업무일지는 ERP의 기능 가운데 먼저 시범 운영한 부분이다. 시범 운영에서는 역할을 팀장·강사·다른 팀 세 가지로
고정했고 사람을 이름으로 연결했다. 자료실·권한 관리와 한 시스템에 두려면 다음을 정해야 했다.

- 역할이 코드에 고정돼 있으면 역할 이름이나 구성을 바꿀 때마다 배포가 필요하다.
- 사람을 이름 문자열로 연결하면 이름이 바뀌거나 같을 때 자료가 어긋난다.
- 다른 담당자의 보고는 응답을 만들 때의 필터가 아니라 조회 조건으로 가려야 한다.

## 결정

업무일지를 `worklog` 모듈로 두고 사람은 계정 ID로만 가리킨다. 역할은 학원이 권한 엔진에서 구성한다.

- `worklog.*` 권한 12개를 둔다. 화면 요청은 다른 기능과 같이 권한 엔진을 거친다.
- `worklog`는 권한 엔진에 의존하지 않는다. "업무를 받는 사람", "보고를 쓰는 사람"은 호출하는 쪽이 권한 원장에서
  구한 계정 집합으로 넘긴다.
- "본인의 것" 조건(담당 업무, 본인 보고, 담당 반, 개인일정)은 `worklog`가 계정 ID로 확인한다. 권한 엔진의 ACL로
  표현하지 않는다.
- 일일보고의 제출 조건은 서버가 계산한다.

## 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 업무·보고마다 ACL을 부여 | 담당자가 바뀔 때마다 ACL을 맞춰야 하고, 담당 관계는 이미 업무 원장에 있음 |
| `worklog`가 권한 엔진을 직접 호출 | 모듈이 서로를 알게 되고, 역할 없이 업무 규칙만 테스트하기 어려워짐 |
| 권한 엔진에 "소유자" 개념 추가 | 소유의 뜻이 자료마다 달라(담당자, 작성자, 담당 반) 공통 규칙으로 묶이지 않음 |

## 결과

역할 이름을 바꾸거나 새 역할을 만들어도 코드가 바뀌지 않는다. 전원 배정 업무의 담당자가 역할 변경을 따라 달라진다.
권한 검사가 컨트롤러와 `worklog` 두 곳에 나뉜다: 기능을 쓸 자격은 컨트롤러, 대상이 본인의 것인지는 `worklog`.
어느 쪽도 빠지면 안 되므로 두 층을 각각 테스트한다.
